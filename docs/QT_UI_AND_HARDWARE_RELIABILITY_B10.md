# DriveRepair 0.3.3b10: Qt recovery UX and hardware reliability

## What changed in this cycle

- **Quick Scan/Quick Repair map the entire disk**, using seeded stratified random addresses and bounded locality groups. Quick Repair continues to request **at least 10% unique address coverage** (not 10% of a prefix). Quick read-only checks in the Qt interface now use the same 10% planner. Each run receives a recorded new random seed, so consecutive scans can examine different locations. A seeded scan is reproducible from its final report. A 10% sample is NOT a full media verification.
- **Qt progress fixed:** sampled scans previously displayed their progress fraction as a percentage without multiplying by 100. `1.0%` could mean 100% of planned samples. Qt now shows a real percentage and a **time-left estimate** when available. The recent transfer-rate and job-average cards remain separate.
- **Truthful 100%-of-drive map:** every cell has a stable byte-offset interval covering the full device. Green fills only the fraction of that cell actually read successfully, not the whole multi-gigabyte cell. Red/orange stripe indicators report observed failed/slow *requests*, not proof that every byte in a cell is bad. Hover for byte offsets and observed coverage. Repeated reads do not increase unique coverage.
- **Simple guided workflow:** Fix / Recover / Check goal buttons now filter the operation menu; scanning-only choices are not presented inside the Fix goal. Contextual information icons explain repair risks, progress, error counts, disk selection, and the map.
- **USB resume (read-only scans):** when a read-only full scan or the SCANNING phase of Full Repair with an opted-in metadata checkpoint stops due to a disconnect, Qt can monitor device reappearance and automatically launch `scan --resume-scan` after matching the stored hashed media identity and capacity. Users can disable this or cancel the reconnect watch. Resume still invokes the authoritative CLI disk-identity check and fails closed when Windows cannot respond. The checkpoint contains offsets and error metadata, NOT recovered files or sector bytes.
- **Read-only OS inspection:** `inspect-storage --device <ID> --json` reports Linux sysfs queue properties, macOS diskutil information, or Windows STORAGE_DEVICE_DESCRIPTOR, access alignment, and disk length using `DeviceIoControl` directly. This probe is isolated from write authorization. In particular, the Windows native inspector does not prove `IsBoot`/`IsSystem`; a successful inspection **must never replace** the write-authorizing `Get-Disk` check. The Qt Drive Details button runs the inspector separately, with a bounded timeout.
- **Experimental Rust firmware-inspection trait:** identifies likely manufacturer from the model string for future **read-only** inventory. It never sends vendor-specific commands and cannot authorize firmware writes or translator changes. Rust compilation must pass on CI: Cargo was not available in the development environment.

## Critical limits and manufacturer support

1. **Windows `Get-Disk -Number` timeout is a safety blocker for physical writes.** Even if the native read-only query works, this release does not bypass boot/system disk confirmation. Check USB dock power, bridge firmware, drivers, port, Windows storage event logs, and another computer. Report `WinError` separately from Python `errno`.
2. **USB disconnect during an active RAM-only write cannot be resumed safely** if the process or machine loses the active original bytes. An entire in-place refresh is not an atomic disk operation. A durable journal on a *separate healthy drive* and renewed media identity are needed before resuming. Even that requires controlled torn-write/disconnect testing per USB bridge; no automatic write restart ships here.
3. **Do not flash firmware based on vendor name or guessed commands.** The model, revision, controller and access method must match an independently validated support matrix. Standard firmware updates must use authenticated manufacturer firmware and compatible vendor tools. There is no universal Seagate/WD/Toshiba vendor-specific repair command. Firmware service-area edits, translator rebuild, FTL bypass and SMART-log clearing are not supported by this beta.
4. **AI outputs are hypothesis/preview data only.** Classification can help find file fragments, but generated bytes cannot be declared recovered originals or written back to the patient disk. Keep a byte-exact evidence image and a separate clearly labeled speculative reconstruction.
5. **SMART and operating-system data are limited by adapters.** The ST1000LM048 is documented SMR even if the transport reports `USB`. Linux rotational/queue attributes do not establish CMR vs SMR; macOS and Windows may expose only the USB bridge. `max_sectors_kb` is a driver request limit, not necessarily the optimal application read size.
6. **A physical HDD may be near failure.** Multiple Windows error 1117 responses, very slow reads and `Get-Disk` timeouts do not establish that software refresh will improve longevity. Preserve irreplaceable data separately before additional stress.

## Recommended operator workflow

- For failed-data recovery: stop additional writes, use a separate healthy destination for multipass image rescue, then repair extracted copies or the image. For one-drive in-place emergency work, the RAM-only override remains explicitly high risk.
- For a simple health check: select **Check drive**, inspect media/OS properties, choose an appropriately bounded read-only check. A 10% scan is substantial work on a 1 TB HDD; budget for seek overhead and retries.
- For intended repair: select **Fix my drive**, review the selected drive's identity, choose Quick or Full targeted repair, and explicitly authorize write risk. The engine only rewrites consistently readable candidates; it never manufactures missing bytes. Known SMR devices do not automatically receive neighboring rewrites.
- For a USB unplug during a full scan: reconnect the same drive; the Qt screen can watch for a matching media identity and resume read-only progress. **It will not automatically restart destructive writes.** If Windows refuses to identify the disk, stop until Windows storage and the dock are responsive.

## Validation / release gates

- Available: Python unit and synthetic fault-injection tests, CLI/package smoke tests, code compilation with Python.
- **Not validated here:** native Qt clickthrough (PySide6 unavailable in this environment); Windows DeviceIoControl requests on live hardware; PowerShell timeouts under bridge failure; in-place write reconnect/torn-journal recoveries; BIOS/UEFI boot; Rust native build and tests; competitive benchmarks.
- Public beta physical-write safety and vendor firmware repair remain blocked pending sacrificial hardware testing and independent security review.
