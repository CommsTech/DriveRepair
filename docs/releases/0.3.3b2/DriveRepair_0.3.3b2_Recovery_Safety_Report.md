# DriveRepair 0.3.3b2 — Recovery progress and automation safety hotfix

**Source:** User-supplied `DriveRepair-main(6).zip`, extracted and reviewed on November 1, 2026.  
**Status:** Tested synthetic release candidate; **NOT qualified for live patient-disk writes, unrestricted public beta, Windows PowerShell execution, or BIOS/UEFI boot**.

## Trigger and diagnosis

The supplied progress transcript includes `RESCUE cursor=... recovered=...` lines and occasional repeated or decreasing cursor values. The current source already implements compact `RescueTerminal` and JSONL progress. The legacy line form remains in old release patches and a historic invocation path; that log may have been generated by a previously running process or different installed module. The transcript alone does not prove durable-map rollback.

Four more serious source-confirmed issues appeared in Windows lab scripts:

1. **Sparse-image length mistaken for recovery progress:** a full-sized output file can be allocated before any patient bytes have been copied. `watch_and_continue_samsung_lab.ps1` used `$len -ge $TargetBytes` as a success signal; `run_elevated_samsung_pm841_lab.ps1` treated an image over 1 MiB as sufficiently present for follow-up.
2. **Automatic patient writes after imaging:** several scripts chained `refresh-external` regardless of verified rescue completion. Even a complete operating-system read is not proof of clean file contents.
3. **Uncoordinated resume and process force-kill:** one script force-stopped broadly matched Python processes. None imposed a recovery writer lock, so multiple launches could contend for the same map/output.
4. **Misleading progress display:** the resume script streamed raw standard error; the logger mixed stdout JSON and stderr in one metrics file, defeating structured reporting.

## Implemented changes

| Area | Modification |
|---|---|
| `desktop/driverepair_desktop/recovery.py` | Added `inspect_rescue_status` to validate journal structure, destination size, and byte accounting; added OS-level exclusive writer lock held across CLI forward and retry passes; lock remains a tiny sidecar, OS ownership released automatically on exit/crash. |
| `desktop/driverepair_desktop/cli.py` | Added read-only `rescue-status --output FILE --json`, with successful exit only if `clean_rescue_complete` is true. |
| `desktop/scripts/resume_samsung_rescue_then_continue.ps1` | Removed broad process-kill behavior and automatic refresh; now refuses a competing live recovery, resumes based on committed map state, reads JSONL status, shows PowerShell progress, and stops on incomplete results. No hard-coded user checkout path. |
| `desktop/scripts/watch_and_continue_samsung_lab.ps1` | Converted to read-only journal watcher, with optional `-Once` and no automatic resume/write/repair. No hard-coded process ID or image-length completion rule. |
| `desktop/scripts/run_elevated_samsung_pm841_lab.ps1` | Requires explicit device, fingerprint and destination; fails if a command fails; only advances after clean journal-based rescue; captures stdout/stderr separately; no automatic `refresh-external`. |
| `desktop/tests/test_rescue_status.py` | Added regression cases for preallocated images, invalid maps, missing outputs, writer exclusion and the lab-script safeguards. |
| README, desktop README, CHANGELOG, `docs/RESCUE_PROGRESS_AND_LAB_SAFETY.md` | Documented journal interpretation, old progress output, safe manual resume, one-writer ownership, and limits of OS-read verification. |

No kernel drivers, device write primitives, raw sector repair algorithms, or firmware operations were changed. This hotfix focuses on preventing false completion and avoiding accidental patient writes.

## Operator guidance (current drive rescue)

**If a rescue is still running, do not start a second job or delete the image/journal.** The updated lock can only coordinate cooperating processes that run the updated code; it cannot manage already-running old versions.

From the revised desktop module:

```powershell
python -m driverepair_desktop rescue-status --output 'D:\RecoveryLab\images\patient_multipass.img' --json
python -m driverepair_desktop gui
```

Check `cursor_bytes`, `recovered_bytes`, `unprocessed_bytes`, `unreadable_bytes`, and `clean_rescue_complete`. An image's logical byte size is not reliable progress information. The status command intentionally exits `2` when incomplete, despite successfully printing a valid status JSON object.
